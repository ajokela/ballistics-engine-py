# MBA-1295 Phase 1 — ballistics-engine-py binding extension

Branch: `mba-1295-binding` (off `main` @ v0.24.0). Engine dependency stays pinned to
`ballistics-engine = "0.24.0"` in Cargo.toml — only this crate's own version bumped.

## Surface-by-surface notes

### 1. One shared parser
- New `src/inputs.rs` hosts the canonical `ballistic_inputs_from_dict` (moved from
  `fast.rs`) + a new `full_to_si` conversion helper (generalizes `geometry_mass_to_si` +
  the ad hoc unit-conversion blocks previously duplicated in `calculate_zero_angle` and
  `monte_carlo_parallel::mc_inputs_to_si`).
- `fast.rs` re-exports `ballistic_inputs_from_dict`/`geometry_mass_to_si` via
  `pub(crate) use crate::inputs::{...}` so `fast_integrate`/`derivatives`/
  `calculate_zero_angle` (and `montecarlo.rs`/`effects.rs`, which reference them as
  `crate::fast::...`) needed zero call-site changes — pure relocation, no behavior change
  to those three pyfunctions.
- Two key vocabularies now resolve onto the same fields: the legacy 11 imperial keys
  (`bc`, `bullet_weight_grains`, `muzzle_velocity_fps`, `bullet_diameter_inches`,
  `bullet_length_inches`, `sight_height_inches`, `zero_distance_yards`,
  `shooting_angle_degrees`, `twist_rate_inches`, `is_right_twist`, `drag_model`) and the
  richer keys fast.rs already understood (`bc_value`, `bullet_mass`, `altitude`,
  `enable_coriolis`, `bc_segments`(+data), `custom_drag_function`, powder temp/curve,
  `shot_direction`, wind shear, cluster BC, ...), plus new keys: `cant_angle_degrees`,
  `enable_trajectory_sampling`, `sample_interval_m`, `use_rk4`, `use_adaptive_rk45`,
  `sight_height_inches`/`muzzle_height_inches`/`target_height_inches` (now actually read —
  previously hardcoded to 0.0 regardless of dict content on the fast path), and
  `custom_drag_table` (list of `[mach, cd]` pairs, validated via `DragTable::try_new`,
  surfacing `ValueError`).
- `PyBallisticInputs` was redesigned to wrap the full engine `RustBallisticInputs` as its
  single source of truth (`inner` field) instead of a 10-field imperial struct. The
  original legacy getters/setters (`bc`, `bullet_weight_grains`, ...) are now computed
  properties over `inner`, plus new getters/setters for the MBA-1295 fields. This was
  necessary for "one parser": previously `from_dict` and `to_rust()` only round-tripped the
  original 10 fields, so anything richer parsed by the shared function would have been
  silently discarded before ever reaching `TrajectorySolver`.
- **Found + fixed in passing**: pyo3's blanket tuple `FromPyObject` only accepts actual
  Python tuples, not lists — so `bc_segments`/`custom_drag_table` extraction would reject
  the JSON-shaped `[[mach, cd], ...]` list-of-lists a Flask/JSON caller actually sends
  (only accepting `[(mach, cd), ...]`). Fixed both `extract_bc_segments` and
  `resolve_custom_drag_table` to extract each row as `Vec<f64>` (accepts both shapes).
  Verified before/after with a direct Python repro.

### 2. Solver setters
`PyTrajectorySolver` gained `set_max_range(range_m)`, `set_time_step(step_s)`,
`set_wind_segments(segments)` (accepts 3-tuples `(speed_kmh, angle_deg, until_m)` or
4-tuples adding `vertical_mps`, mixed in the same call), and `set_atmo_segments(segments)`
(4-tuples `(temp_c, pressure_hpa, humidity_percent, until_distance_m)` — cheap because the
engine's `AtmoSegment` is already a plain tuple type alias, no conversion needed).

### 3. WindConditions.vertical_speed_mps
Added as a 3rd optional constructor arg (default 0.0) and a plain get/set field — no
imperial conversion (engine-native m/s already).

### 4. Result exposure
`TrajectoryResult` gained `sampled_points: Optional[List[dict]]` (each row:
`distance_m, drop_m, wind_drift_m, velocity_mps, energy_j, time_s, flags: List[str]`,
`None` when sampling is off) and `transonic_mach: Optional[float]` passthrough.

### 5. Zero integration
New `auto_zero_inputs(inputs_dict, zero_distance_yards, target_height_inches=0.0,
wind=None, atmo=None) -> muzzle_angle_rad`, wrapping
`calculate_zero_angle_with_conditions` via the same shared parser. `wind`/`atmo` override
the dict's own `wind_speed`/`wind_angle`/`temperature`/`pressure`/`humidity`/`altitude`
when supplied.

### 6. Engine Monte Carlo
New `run_monte_carlo(inputs_dict, params_dict, wind=None, atmo=None, hit_radius_m=None)
-> dict`, wrapping `run_monte_carlo_with_wind_and_direction_std_dev`. `params_dict` mirrors
`MonteCarloParams` field-for-field in the engine's own SI units (velocity_std_dev m/s,
angle_std_dev/azimuth_std_dev radians, target_distance meters, ...) plus
`wind_direction_std_dev` (a separate argument on the wrapped engine function). Returns
`hit_probability`, `target_plane_cep_m`, `target_arrival_count`,
`target_shortfall_fraction`, `num_samples`, `ranges_m`, `impact_velocities_mps`,
`impact_positions_yz_m`. Atmosphere has no separate parameter on the wrapped engine
function (it derives its own `AtmosphericConditions` from the inputs struct's
temperature/pressure/humidity/altitude), so `atmo=` writes those 4 fields on the parsed
inputs before calling it — matching `auto_zero_inputs`.

### 7. Tests
New `test_mba1295.py` (11 test functions, plain-python + asserts, matching this repo's
`test_bindings.py` convention — no pytest dependency). Covers: legacy-key backward compat
+ documented defaults, new property round-trips, rich keys on the solver path, cant
tilting POI right+low (mirrors the engine's own
`cant_sign_clockwise_up_offset_goes_right_and_low` unit test), vertical wind raising POI
(mirrors `updraft_raises_poi_downrange`), custom drag table changing drop + validation
errors, trajectory sampling rows, mixed 3/4-tuple wind segments, atmo segments, auto-zero
landing near the sight line, and Monte Carlo `hit_probability ∈ [0, 1]`.

### 8. Version
`Cargo.toml` `[package] version` 0.24.0 → 0.24.1. `ballistics-engine` dependency left at
`"0.24.0"` per instructions.

## Review fixes (second commit)

- **CRITICAL (MC sight_height leak)**: `monte_carlo_parallel`'s boundary
  (`mc_inputs_to_si`) now explicitly zeroes `sight_height`, `muzzle_height`, AND
  `target_height` before solving. The engine's `solve_trajectory_for_monte_carlo` computes
  `drop = (muzzle_height + sight_height) - final_y` (monte_carlo.rs: `line_of_sight_y =
  bore_y + inputs.sight_height`), and the pre-MBA-1295 parser hardcoded all three datum
  fields to 0.0 — so MC drop has always been BORE-relative. muzzle_height/target_height
  were zeroed alongside sight_height because muzzle_height enters the exact same formula
  (the review's own formula names it) and all three shared the same pre-MBA-1295 hardcode;
  zeroing only sight_height would leave the same class of leak open via the
  `muzzle_height` dict key. The shared parser itself was NOT changed for this fix.
- **IMPORTANT (sight_height default)**: the shared parser's missing-key default for
  `sight_height`/`sight_height_inches` restored from 0.0 to the legacy-documented
  1.5 inches (0.0381 m after `full_to_si`). Verified the engine's fast kernel
  (`fast_trajectory.rs`) and `derivatives.rs` never read the datum fields, so
  `fast_integrate`/`derivatives` are insensitive to this default either way.
- **Locking tests added** (both in `test_mba1295.py`):
  - `test_from_dict_missing_sight_height_defaults_to_1_5_inches` — from_dict without the
    key (and from `{}`) carries 1.5 in / 0.0381 m. PASS.
  - `test_monte_carlo_parallel_drop_is_bore_relative` — Flask-shaped MC dict with
    `sight_height: 1.5` produces mean drop identical (1e-12) to the same dict with
    `sight_height: 0.0` AND to the dict with the key absent (parser default 1.5 also
    zeroed); a leak would shift it by exactly 0.0381 m. PASS.
- Re-verified after the fixes: `cargo check --release` clean, `cargo clippy --release
  --no-deps -- -D warnings` clean, `maturin build --release` OK, wheel reinstalled,
  `test_mba1295.py` 13/13 test functions pass, `test_bindings.py` passes,
  `__version__ == 0.24.1`.

## Concerns / things the controller should know

1. **Relaxed "required key" strictness on the fast path.** The original
   `ballistic_inputs_from_dict` raised `PyKeyError` if `bc_value`/`bc_type`/`bullet_mass`/
   `altitude` were absent. The merged parser makes all four alias-then-default instead
   (matching `PyBallisticInputs`'s pre-existing "missing keys fall back to defaults"
   contract, which is the more specific documented promise for the deliverable this phase
   is about). This means `fast_integrate`/`calculate_zero_angle`/`monte_carlo_parallel`
   called with an incomplete dict now silently defaults those 4 fields rather than
   erroring. No existing test in this repo exercises that error path, and this binding's
   rich-dict entry points have no production consumer yet per the ticket's own recon, so
   the risk looks low — flagging for visibility since it's a real, intentional contract
   change.
2. **Default value change for 5 rich-only fields.** `muzzle_velocity`, `twist_rate`,
   `bullet_length`, `bullet_diameter`, `target_distance` previously defaulted to `0.0` in
   the fast-path parser when their rich key was absent (not aliased from a legacy key).
   The merged parser defaults them to `PyBallisticInputs`'s own defaults (2650 fps, 11.25",
   1.2", 0.308", 100 yd) instead, so `from_dict`'s documented default-fallback contract
   holds. A rich-dict caller who omits e.g. `muzzle_velocity` (previously got 0.0, which
   would fail/degenerate almost immediately) now gets 2650 fps. Same "no production
   consumer yet" mitigation as above.
3. **Pre-existing (untouched) unit-conversion quirk noticed, not fixed.** `fast.rs`'s
   existing `calculate_zero_angle` pyfunction does `bi.twist_rate *= INCHES_TO_METERS`
   after parsing, but `BallisticInputs::twist_rate` is documented "inches per turn" (native
   unit, no SI conversion) and every other code path (this binding's own
   `PyBallisticInputs::to_rust`, the engine's own tests) leaves it in inches. This looks
   like a latent bug in that one pre-existing function, degrading twist-rate-dependent
   effects (spin drift, Magnus) for zero-angle solves specifically. Left untouched (out of
   this phase's scope — `calculate_zero_angle` isn't one of the deliverables); the new
   `auto_zero_inputs` does NOT replicate it (uses `full_to_si`, which leaves twist_rate in
   inches, consistent with the field's documented unit).
4. **`use_adaptive_rk45` default differs by construction path.** `PyBallisticInputs::new()`
   (bare constructor) still defaults to the engine's own `BallisticInputs::default()`
   baseline, where `use_adaptive_rk45 = true`. `PyBallisticInputs::from_dict()` (via the
   shared parser) defaults it to `false` (matching the historical fast-path hardcode).
   Both are unchanged pre-existing defaults for their respective paths — just noting the
   asymmetry is now more visible since both paths funnel through the same struct.
